# ソープ表現 課題管理表

`soap.rs`（GPU常駐Foam Instance Pool + 2Dメタボール直接評価、[soap-model.md](soap-model.md) の実装）を
レビューして洗い出した課題一覧。起点は実機確認で報告された「泡っぽい形にはなるが、毎回同じ形になる」
という症状で、そこから静的コードレビューで見つかった関連課題を合わせて記載する。

**2026-07-28追記**：S-01〜S-08への対症療法（パラメータ調整・ノイズ追加）を検証する過程で、
根本原因は「泡ではなく粘性液体の力学モデルを使っていたこと」と「`soap_compute.wgsl`が
`bubble.rs`のAvianボディと知らずに二重に物理（特に重力）を解いていたこと」の2点にあると
判明した。[soap-model.md](soap-model.md) 第27〜30節でPhase計画ごと設計を改訂し
（Particle=液体の小片 → Particle=Foam Aggregate、Avianをマクロ力学の一次情報源にする）、
本表もそれに合わせて更新している。続く第31節では、命名（GPU Particle Pool →
GPU Foam Instance Pool）・所有権（Entity⇔スロット対応をResourceではなくEntity自身の
Component `FoamGpuBinding` に持たせる）をさらに精緻化し、その過程でS-10（スロット再利用時の
変形状態残留）を発見・修正している。

**2026-07-29追記（3Dトップダウン→2Dサイドビューへの方針転換）**：この時点では物理エンジンは
Avian3D、粒子座標は`vec3`、描画は`Transparent3d`フェーズへのレイマーチだったが、この日を境に
Avian3D→**Avian2D**（`avian2d` crate）、`vec3`→`vec2`、レイマーチ→**ピクセルごとの密度場直接評価**
（`Transparent2d`フェーズ）へ全面的に置き換えた。ハンドソープ筐体を真横から見るサイドビューでは
奥行き方向のマーチが不要になるため、着地判定・扁平化の式自体は変えずに`vec3`を`vec2`にするだけで
成立する（詳細は`soap_compute.wgsl`/`soap_render.wgsl`冒頭のコメント、および
[soap-model.md](soap-model.md)の現状追記を参照）。この方針転換に伴って生まれた新規課題
（融合が硬い輪郭になる・浅い着地で扁平化しない・射出直後から丸い等）をS-16〜S-32として追加した。
以降のS-XXの「原因」欄で言及する`Avian`は特記が無い限りAvian2Dを指す。

## 備考

- S-01・S-02・S-03 が「毎回同じ形に見える」問題の直接の症状で、S-09（重力の二重管理）がその奥にあった構造的な根本原因だった。パラメータ調整（S-01〜S-03）は症状を緩和したが、S-09の解消（Avian駆動化、[soap-model.md](soap-model.md) 第27〜28節）でモデルの前提そのものが「液体」から「泡の集合体」に変わり、S-02・S-04は問題の前提条件ごと消滅している。
- S-10はS-09の実装（永続的なEntity⇔スロット対応）そのものが持ち込んだ新しい課題で、同じ実装パス内で世代番号（generation）により解決した。「以前は無かった種類のバグ」を設計変更が持ち込みうる、という一例として記録している。
- S-11はS-11a（静的Quality Profile）とS-11b（Auto Dynamic Quality）に分割した。S-11aを先に完成させ実機ベンチマークを取ってからでないと、S-11bのヒステリシス閾値は「当てずっぽう」になってしまうため、意図的にS-11bを後回しにしている。
- S-12・S-13・S-14は、実際に実機（GTX 1650 SUPER）で動かして初めて見つかった問題。`cargo check`はRust側の型・借用エラーしか検出できず、GPU上のループ回数・密度場の妥当性・「Avianの物理挙動とシェーダー側の前提が本当に噛み合っているか」は検証できない。特にS-14（着地判定がAvianの実際の静止位置＝半径分浮いた高さを考慮していなかった）は、Avian駆動化（S-09）の設計自体は正しくても、細部の物理的前提（球が床にめり込まない）を見落とすと簡単に壊れることを示す例。S-11a〜S-14を通じて「コンパイルが通ること」と「実際に動くこと」は別問題であることが具体的に裏付けられた。
- S-16〜S-32は2026-07-29の3D→2D方針転換（前掲の追記参照）にあわせて発生・発見された課題群。S-17/S-23（飛行中Bubble同士の連結）とS-24（着地済み泡だまりへの積み上がり）は同じ「Bubble×Bubble衝突をどう扱うか」という問題の異なる側面で、最終的に「飛行中は非衝突・着地済み(LandedBubble)とは衝突」という2レイヤー構成に落ち着いた。S-25〜S-27・S-29はこの2レイヤー構成を実際に動かして初めて見つかった副作用（かまくら状の固着・軌跡が蛇状に残る・Kinematic Enemyに押し出される・床との衝突条件の反映漏れ）。S-30〜S-32は「毎回同じ形に見える」というS-01〜S-03と同種の指摘が、Avian駆動化・2Dピボット後の新しいアーキテクチャ（クラスター状のFoam Instance配置）に対して再度出たもので、乱数化の幅を都度広げることで対応した。
- S-06（シーン深度によるオクルージョン、Transparent3d時代の課題）は3D→2D方針転換前に「見送り」判定されたものであり、`Transparent2d`への移行後に同じ課題がどう現れるか（あるいは解消したか）は未再評価。実機で奥行きの前後関係が気になった場合は改めて調査すること。
- S-33・S-34は「もっとハンドソープ（洗顔フォーム）っぽく見えるようにしてほしい」という実機フィードバックから見つかった。S-34は特に、S-24（着地済みの泡だまりへ積み上がる）の実装自体は正しくても、`CollisionLayers`のfiltersにLandedBubble自身を含め忘れるという1行の抜けだけで「山が一切高さを持てない」という機能全体の無効化につながっていた例——ゲームロジックのバグはコンパイルエラーにならないため、実際に触って「泡が積み上がらない」という見た目の違和感から逆算しないと見つからない典型例だった。
- S-37→S-38はS-10と同じ「対策そのものが新しいバグを持ち込んだ」パターン。S-37（横push対策としてのX方向lock）は問題の一面（横に押しのけられる）は解消したが、Avianの接触ソルバーが`LockedAxes`でロックされた軸を無視して残りの自由な軸だけに補正を押し付けるという性質と噛み合わず、より深刻なS-38（垂直方向への異常な弾き飛ばし）を引き起こした。最終的にlockという「特定軸を完全に固定する」アプローチ自体をやめ、`SolverConfig::max_overlap_solve_speed`という「重なりの解消速度に上限を設ける」グローバルな穏当化アプローチに置き換えている——ロック系の対策は柔道の関節技のように「動けない方向に力が集中して壊れる」リスクがあることの実例。
- S-39はS-35（泡は自然に消えなくていい）が持ち込んだ副作用。「泡を消す」機能そのものを撤去したことで、消える前提で設計されていた別の仕組み（S-11aのquality上限＝`max_aggregates`）が暗黙に壊れていた——コンパイルも通り、少数の泡で試す分には気づけず、実際に長時間プレイして初めて発覚する類のバグだった。ある機能（時間経過での消滅）を撤去するときは、その機能の「消える」という前提に依存している他の仕組みが無いか（本件では有限のGPU描画予算という別の理由で"消える"ことを前提にしていた）を横断的に確認する必要がある、という教訓として記録する。
- S-06とS-11bのみ見送り／後回し。他は全て対応済み（S-13は実機での見た目次第で追加調整が必要な可能性あり）。
- 全ての変更は `cargo check` でRust側のコンパイルを確認済み。ただしWGSLの構文・実行時の見た目は未実行で未検証（コンパイル不要という指示だったため）。実際に `cargo run` して見た目を確認することを推奨。
